    69→### 1.2 Layer Hierarchy (Intended)
    70→
    71→| Layer | Files | Purpose |
    72→|-------|-------|---------|
    73→| **L0 — Constants** | `constants.py` | Magic numbers, severity maps, paths |
    74→| **L1 — Utilities** | `utils.py`, `security.py`, `theme.py`, `interfaces.py` | Pure functions, no reconpro imports |
    75→| **L2 — Core** | `http_layer.py`, `registry.py`, `modules/__init__.py` | HTTP, module registry, Finding dataclass |
    76→| **L3 — Engine** | `scanner.py`, `engine.py`, `parallel.py` | Orchestration, sync + async |
    77→| **L4 — Intelligence** | `ai_analyst.py`, `attack_graph.py`, `threat_intel.py`, `intelligence_pipeline.py` | Post-scan analysis |
    78→| **L5 — Outputs** | `reports.py`, `formats.py`, `report_writer.py`, `observability.py` | Rendering, export, logging |
    79→| **L6 — Entry Points** | `cli.py`, `server.py`, `chat.py`, `nexus_tui.py`, `agent.py` | User-facing interfaces |
    80→
    81→### 1.3 Key Architectural Decisions
    82→
    83→1. **Dual scan engines**: `scanner.py` (sync, sequential) and `engine.py` (async, concurrent) — both expose identical `scan()`/`audit_scan()` signatures
    84→2. **Lazy module loading**: `registry.py` defers all 23 module imports via `_get_runners()` cache
    85→3. **Pure Python constraint**: No external runtime dependencies (only optional: `rich`, `aiohttp`, `openai`)
    86→4. **Event-driven async**: `engine.py` emits `ScanEvent` objects for TUI/dashboard integration
    87→5. **Plugin hooks**: In-process hook system via `plugins.py` (`pre_scan`, `post_scan`, `post_finding`)

    93→### 2.1 CRITICAL Issues
    94→
    95→#### C-01: Dual Scan Engines Create Divergent Behavior Risk
    96→
    97→**Files:** `scanner.py:59-152`, `engine.py:600-658`
    98→
    99→Both `scanner.scan()` and `engine.scan()` claim to be drop-in replacements for each other, but they have **subtle behavioral differences**:
   100→
   101→- `scanner.scan()` validates targets via `validate_target()`; `engine.scan()` does **not**.
   102→- `scanner.scan()` handles the vibesec 4-tuple return explicitly; `engine.py` detects it via `isinstance(result, tuple) and len(result) == 4` — fragile, will break if any other module returns a 4-tuple.
   103→- `scanner.scan()` calls no plugin hooks; `engine.run()` fires `pre_scan` and `post_scan` hooks.
   104→- `scanner.scan()` does not run the Intelligence Pipeline; `engine.run()` does.
   105→- `scanner.py` uses `count_severities()` from utils; `engine.py:232-234` manually counts severities inline.
   106→
   107→**Impact:** Consumers importing from `scanner` vs `engine` get different behavior. `__init__.py:72` exports from `scanner` (the old sync path), but `agent.py`, `nexus_agent.py`, `adversarial.py`, and `swarm.py` import from `engine` (the new async path).
   108→
   109→**Recommendation:** Deprecate `scanner.scan()`/`scanner.audit_scan()` in favor of `engine`. Update `__init__.py` to export from engine. Add `validate_target()` call to engine.

   114→
   115→**Files:**
   116→- `constants.py:86-89` — `"ReconPro/10.0 (Enterprise Security Scanner; ...)"`
   117→- `http_layer.py:41-44` — `"ReconPro/10.0 (Enterprise Security Scanner; ...)"`

   119→- `connection_pool.py:43-46` — `"ReconPro/2.0 (Enterprise Security Scanner; ...)"` ← **STALE**
   120→- `__init__.py:69` — version is `"10.0.0"`

   190→#### H-04: Three Competing HTTP Layers Without Clear Ownership
   191→
   192→| Module | Approach | Used By |
   193→|--------|----------|---------|
   194→| `http_layer.py` | `urllib.request`, per-request SSL, 166 LOC | Most modules (23+), scanner.py, engine.py |
   195→| `connection_pool.py` | `urllib.request`, cached SSL, pooled headers, 256 LOC | profiler.py (few files) |
   196→| `async_http.py` | `aiohttp` (optional) + urllib fallback, 903 LOC | engine.py (async path) |
   197→
   198→**Issues:**
   199→- All three implement nearly identical `probe()` functions with the same return shape
   200→- All three hardcode `_BODY_LIMIT = 16384` independently instead of importing from `constants.DEFAULT_BODY_LIMIT`
   201→- `connection_pool.py` is barely used despite having better performance (cached SSL contexts)
   202→- `async_http.py` doc says "No direct imports from `.http` are used to avoid circular dependencies" — reveals fragility in the HTTP layer relationship
   203→
   204→**Impact:** Bug fixes to HTTP handling (e.g., timeout behavior, header handling) must be applied in 3 places. Modules choose inconsistently which layer to use.
   205→
   206→**Recommendation:** Consolidate into a single HTTP abstraction with sync/async modes. `connection_pool.py`'s SSL caching should be the default. All modules should go through one entry point.

   210→#### H-05: `cli.py` is a 2014-Line Monolith
   211→
   212→**File:** `cli.py` (2014 lines)
   213→
   214→The `main()` function (starting ~line 250) is a single massive function handling 40+ subcommands with inline parsing, execution, and rendering for each. There is no command pattern, no subcommand dispatch table, no separation of concerns.
   215→
   216→**Cyclomatic complexity estimate:** The `main()` function alone has 40+ `if args.subcommand == ...` branches, plus nested conditionals, easily exceeding cyclomatic complexity of 80+.
   217→
   218→**Impact:**
   219→- Extremely difficult to test individual commands in isolation
   220→- Adding a new subcommand requires modifying a 1700+ line function
   221→- Import-time side effects: module-level `Console()` and `Theme.current()` calls at lines 24, 37
   222→
   223→**Recommendation:** Extract each subcommand into its own handler function/class. Use a dispatch table (dict mapping subcommand name → handler). See `cli_help.py` (1003 LOC) as evidence the monolith is already being split.

   272→
   273→**Files:** `ai_analyst.py:34-100` (`ExtendedFinding` — 20+ fields), `threat_intel.py:56-87` (`EnrichedFinding` — 12 fields), `http_layer.py:108-133` (`Finding` — 11 fields)

   288→#### M-04: Intelligence Pipeline Always Runs After Scans in Engine
   289→
   290→**File:** `engine.py:483-496`
   291→

   601→## 6. Circular Import Analysis
   602→
   603→The codebase largely avoids circular imports through these patterns:
   604→
   605→1. **Lazy imports inside functions** — `engine.py:312-313`, `engine.py:415-416`, `engine.py:487-488` use `from .plugins import HookManager` inside function bodies
   606→2. **`__future__ import annotations`** — Used universally to defer type evaluation
   607→3. **`utils.py` isolation** — Only imports from `constants.py`, never from other reconpro modules
   608→
   609→**Potential circular import risks (not currently broken but fragile):**
   610→
   611→| Risk | Chain | Current Mitigation |
   612→|------|-------|-------------------|
   613→| `engine` ↔ `plugins` | engine imports plugins (lazy) → plugins may import scanner/engine | Lazy import inside function body |
   614→| `engine` ↔ `intelligence_pipeline` | engine imports pipeline (lazy) → pipeline imports ai_analyst, attack_graph, threat_intel | Lazy import inside function body |
   615→| `cli` → `scanner` → `registry` → `modules/*` → `http_layer` → `scanner` | cli imports scanner which imports registry which imports modules | Not a cycle (modules import http_layer, not scanner) |
   616→| `nexus_agent` → `engine` → `scanner` → `nexus_agent` | If nexus_agent imports engine which imports scanner which imports nexus_agent... | Currently avoided because nexus_agent uses lazy imports |
   617→
   618→**Assessment:** The lazy-import strategy works but is undocumented and fragile. A single eager import added to the wrong file could break the chain. Consider documenting the dependency graph and adding an import-cycle CI check.
