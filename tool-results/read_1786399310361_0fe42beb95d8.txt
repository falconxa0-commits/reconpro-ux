    80→    80→
    81→    81→### 1.3 Key Architectural Decisions
    82→    82→
    83→    83→1. **Dual scan engines**: `scanner.py` (sync, sequential) and `engine.py` (async, concurrent) — both expose identical `scan()`/`audit_scan()` signatures
    84→    84→2. **Lazy module loading**: `registry.py` defers all 23 module imports via `_get_runners()` cache
    85→    85→3. **Pure Python constraint**: No external runtime dependencies (only optional: `rich`, `aiohttp`, `openai`)
    86→    86→4. **Event-driven async**: `engine.py` emits `ScanEvent` objects for TUI/dashboard integration
    87→    87→5. **Plugin hooks**: In-process hook system via `plugins.py` (`pre_scan`, `post_scan`, `post_finding`)

    93→    93→### 2.1 CRITICAL Issues
    94→    94→
    95→    95→#### C-01: Dual Scan Engines Create Divergent Behavior Risk
    96→    96→
    97→    97→**Files:** `scanner.py:59-152`, `engine.py:600-658`
    98→    98→
    99→    99→Both `scanner.scan()` and `engine.scan()` claim to be drop-in replacements for each other, but they have **subtle behavioral differences**:
   100→   100→
   101→   101→- `scanner.scan()` validates targets via `validate_target()`; `engine.scan()` does **not**.
   102→   102→- `scanner.scan()` handles the vibesec 4-tuple return explicitly; `engine.py` detects it via `isinstance(result, tuple) and len(result) == 4` — fragile, will break if any other module returns a 4-tuple.
   103→   103→- `scanner.scan()` calls no plugin hooks; `engine.run()` fires `pre_scan` and `post_scan` hooks.
   104→   104→- `scanner.scan()` does not run the Intelligence Pipeline; `engine.run()` does.
   105→   105→- `scanner.py` uses `count_severities()` from utils; `engine.py:232-234` manually counts severities inline.
   106→   106→
   107→   107→**Impact:** Consumers importing from `scanner` vs `engine` get different behavior. `__init__.py:72` exports from `scanner` (the old sync path), but `agent.py`, `nexus_agent.py`, `adversarial.py`, and `swarm.py` import from `engine` (the new async path).
   108→   108→
   109→   109→**Recommendation:** Deprecate `scanner.scan()`/`scanner.audit_scan()` in favor of `engine`. Update `__init__.py` to export from engine. Add `validate_target()` call to engine.

   114→   114→
   115→   115→**Files:**

   119→   119→- `connection_pool.py:43-46` — `"ReconPro/2.0 (Enterprise Security Scanner; ...)"` ← **STALE**

   121→   121→- Banner in `cli.py:33` — says `ELEVEN BLADES` but docstring says `Twenty-Seven Blades`

   190→   190→#### H-04: Three Competing HTTP Layers Without Clear Ownership
   191→   191→
   192→   192→| Module | Approach | Used By |
   193→   193→|--------|----------|---------|
   194→   194→| `http_layer.py` | `urllib.request`, per-request SSL, 166 LOC | Most modules (23+), scanner.py, engine.py |
   195→   195→| `connection_pool.py` | `urllib.request`, cached SSL, pooled headers, 256 LOC | profiler.py (few files) |
   196→   196→| `async_http.py` | `aiohttp` (optional) + urllib fallback, 903 LOC | engine.py (async path) |
   197→   197→
   198→   198→**Issues:**
   199→   199→- All three implement nearly identical `probe()` functions with the same return shape
   200→   200→- All three hardcode `_BODY_LIMIT = 16384` independently instead of importing from `constants.DEFAULT_BODY_LIMIT`
   201→   201→- `connection_pool.py` is barely used despite having better performance (cached SSL contexts)
   202→   202→- `async_http.py` doc says "No direct imports from `.http` are used to avoid circular dependencies" — reveals fragility in the HTTP layer relationship
   203→   203→
   204→   204→**Impact:** Bug fixes to HTTP handling (e.g., timeout behavior, header handling) must be applied in 3 places. Modules choose inconsistently which layer to use.
   205→   205→
   206→   206→**Recommendation:** Consolidate into a single HTTP abstraction with sync/async modes. `connection_pool.py`'s SSL caching should be the default. All modules should go through one entry point.

   211→   211→
   212→   212→**File:** `cli.py` (2014 lines)
   213→   213→

   601→   601→## 6. Circular Import Analysis
   602→   602→
   603→   603→The codebase largely avoids circular imports through these patterns:
   604→   604→
   605→   605→1. **Lazy imports inside functions** — `engine.py:312-313`, `engine.py:415-416`, `engine.py:487-488` use `from .plugins import HookManager` inside function bodies
   606→   606→2. **`__future__ import annotations`** — Used universally to defer type evaluation
   607→   607→3. **`utils.py` isolation** — Only imports from `constants.py`, never from other reconpro modules
   608→   608→
   609→   609→**Potential circular import risks (not currently broken but fragile):**
   610→   610→
   611→   611→| Risk | Chain | Current Mitigation |
   612→   612→|------|-------|-------------------|
   613→   613→| `engine` ↔ `plugins` | engine imports plugins (lazy) → plugins may import scanner/engine | Lazy import inside function body |
   614→   614→| `engine` ↔ `intelligence_pipeline` | engine imports pipeline (lazy) → pipeline imports ai_analyst, attack_graph, threat_intel | Lazy import inside function body |
   615→   615→| `cli` → `scanner` → `registry` → `modules/*` → `http_layer` → `scanner` | cli imports scanner which imports registry which imports modules | Not a cycle (modules import http_layer, not scanner) |
   616→   616→| `nexus_agent` → `engine` → `scanner` → `nexus_agent` | If nexus_agent imports engine which imports scanner which imports nexus_agent... | Currently avoided because nexus_agent uses lazy imports |
   617→   617→
   618→   618→**Assessment:** The lazy-import strategy works but is undocumented and fragile. A single eager import added to the wrong file could break the chain. Consider documenting the dependency graph and adding an import-cycle CI check.
